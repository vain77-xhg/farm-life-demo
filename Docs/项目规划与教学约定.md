## 四、当前真实项目基线

截至本次更新，Assets 下有 15 个项目 C# 脚本，包含编辑器工具。主要能力如下：

- `Bootstrap` 是现有启动入口，处理单例与 `DontDestroyOnLoad`，运行时创建资源、UI、输入、事件、场景和文本管理器，再传入依赖。`TextManager.Initialize(_resourceManager)` 在 `StartGame()` 加载农场场景前执行；`GetTextManager()` 提供已有组件引用。
- `ResourceManager` 提供 Resources 预制体加载、实例化和 `LoadTextAsset(string path)` 文本资源加载。文本加载成功时返回 `TextAsset`，失败时输出日志并返回 null。
- `TextManager` 保存资源管理器引用，读取 `Data/文本表`，拆分单行 CSV 记录并建立 `Dictionary<int, string>`。`GetText(int textId)` 查询文字，编号缺失时报错并返回空字符串。
- `EventManager` 支持无参数、int 参数和 string 参数事件。
- `InPutManager` 发布界面事件，并提供移动、奔跑和 E 键交互输入查询。
- `SceneLoader` 使用协程等待异步加载，有重复请求拦截、场景可加载检查、进度和完成日志。
- `UIManager` 创建并复用背包与设置预制体；`SettingsUI` 处理关闭按钮。背包目前是界面开关，没有物品存储、数量和格子数据逻辑。
- `FarmSceneController` 创建玩家、传入输入管理器，并设置相机跟随目标。
- `PlayerController` 在 Update 读取方向和交互键，在 FixedUpdate 设置 `Rigidbody2D.velocity`，支持走路和左 Shift 奔跑。
- `CameraFollow` 在 LateUpdate 跟随玩家 X、Y 坐标并保留相机 Z 坐标。
- 交互使用 `Physics2D.OverlapCircleAll` 获取附近碰撞体，通过 `GetComponent<InteractableObject>()` 筛选，再按位置距离选择最近的可交互组件。
- `InteractableObject` 已将直接文字字段替换为 `_textId`；`Interact()` 获取文本管理器、按编号查询，空文字时结束，有文字时输出到 Console。尚未接入游戏内文字面板。
- 农场已有 `TestObstacle` 与 `FarmSing` 两个测试目标，场景分别保存文本 ID 300001、300002；名称以工程实际拼写为准。
- 交互范围使用红色 Gizmos 显示。玩家预制体已保存 `_interactRadius = 0.8`，用户确认手感舒服；脚本中的 `1.5f` 是默认值，不要因此重置预制体配置。
- `GameEvents` 与 `GameScenes` 继续用于事件名称和场景名称。
- 编辑器菜单“工具/打开启动场景”用于打开 `SampleScene`。

启动时要从 `SampleScene` 进入。直接运行没有 Bootstrap 的 `FarmScene`，不能据此认定输入或事件系统断裂。

`Bootstrap.StartGame()` 目前仍保留自动打开背包、创建并隐藏 TestCube 的启动测试。它们属于后续可整理内容，尚未清理。

最近目标选择代码已经实现并做过代码检查。用户明确暂缓了那次多目标运行测试，不要将它写成已通过，也不要把它当成进入文本表教学的前置任务。

已接通 Excel 手动导出、游戏 CSV 加载、`TextManager` 解析查询及场景交互引用。尚未实现：自动导表工具、游戏内交互文字 UI、游戏状态管理、时间系统、物品数据系统、背包存储和存档系统；不因文本基础接通而认定第一阶段完成。

## 五、ID 与配置数据的规划

2026-10-21 确认规则，2026-10-24 更新进度：文本 ID 采用 int 数字编号，通过位数和号段分类，替代此前英文前缀字符串方案。当前已实现文本读取与查询；分类范围是编号约定，当前代码尚未校验号段。

| 位数 | 号段（包含起止值） | 文本类型 | 例子 |
| --- | --- | --- | --- |
| 6 位 | 100000～199999 | 通用界面 | 开始游戏、设置、背包、关闭、音量 |
| 6 位 | 200000～299999 | 操作结果与系统提示 | 背包已满、金币不足、保存成功 |
| 6 位 | 300000～399999 | 场景交互提示 | 路牌内容、门已上锁、按 E 交互 |
| 6 位 | 400000～499999 | 时间与日历 | 春季、星期一、节日名称 |
| 7 位 | 1000000～1999999 | 物品名称与说明 | 胡萝卜、种子介绍、工具说明 |
| 7 位 | 2000000～2999999 | 种植、制作与生产说明 | 作物生长条件、配方说明、加工说明 |
| 7 位 | 3000000～3999999 | 地图与建筑名称、介绍 | 农场、村庄、铁匠铺、建筑介绍 |
| 7 位 | 4000000～4999999 | 角色与怪物名称、介绍 | 村长姓名、人物介绍、怪物说明 |
| 8 位 | 10000000～19999999 | 对话内容与选项 | NPC 日常聊天、商店对话、回答选项 |
| 8 位 | 20000000～29999999 | 任务文本 | 任务标题、目标说明、完成描述 |
| 8 位 | 30000000～39999999 | 信件、剧情与教程 | 信件正文、剧情旁白、新手引导 |

编号与引用约定：

- 上表全部是文本 ID，不代表物品、NPC、任务本身的配置 ID；其他数据类别的数字编号规则另行规划。
- 所有文本 ID 唯一；没有列出的号段与九位 ID 暂时保留，不预先生成空数据。
- 同一句通用文字可以共用 ID；修改文字保留 ID，旧 ID 不分配给无关新文字。
- 位数和号段用于管理与校验，不要求建立不同的文本管理器。文本仍可放在一张表中查询。
- 字段明确写用途，例如 `_textId`、`itemId`、`NameTextId`、`DescriptionTextId`。
- 物品表通过名称文本 ID、说明文本 ID 引用文本表，不能将物品身份与显示文字混在一起。
- 定义 ID 表示“哪一种数据”。需要独立存档的场景实体，以后再设计实例 ID；当前路牌不额外引入实例 ID。

当前 Excel 源表：[文本表.xlsx](DataTables/文本表.xlsx)，由用户制作，按上表 11 个号段分工作表；工作表名称记录范围和用途。原 `Texts.xlsx` 已不使用，不要恢复旧文件，也不要沿用“所有范围说明都在表下方”的旧记录。

当前使用“300000~399999 场景交互提示”工作表，表头是 `ID`、`Text`，两条示例使用 300001、300002。当前导出的 CSV 测试文字为：

| ID | Text |
| --- | --- |
| 300001 | 他说："前方是农田,请爱护作物。" |
| 300002 | 这里是农场入口，欢迎回来！ |

源表保存在 Docs 下，不作为运行时资源加载。修改文字后先保存 `.xlsx` 源表，再将当前数据工作表另存为 CSV UTF-8，更新 `Assets/Resources/Data/文本表.csv`。Excel 导出 CSV 仅保存当前工作表；原 `.xlsx` 保留全部工作表。当前只有这一份游戏 CSV，多分类自动合并或分别导出尚未实现；不要把其他空表或说明混入数据。

未来关联示例（尚未实现）：背包保存物品 ID 和数量 → 物品配置提供名称文本 ID（例如 1000001）→ 文本表返回“胡萝卜”→ 界面显示。

## 六、当前文本数据流与职责

```text
Excel / WPS 编辑 ID、Text
    → 用户导出 UTF-8 CSV
    → Unity 导入为 TextAsset
    → Bootstrap 初始化 TextManager
    → ResourceManager.LoadTextAsset("Data/文本表") 返回资源
    → TextManager.LoadTexts() 解析并保存 Dictionary<int, string>
    → InteractableObject.Interact() 使用自己的 _textId 查询
    → TextManager.GetText() 返回文字
    → 当前输出到 Console，后续可接游戏 UI
```

实际 CSV：`Assets/Resources/Data/文本表.csv`；Resources 路径：`Data/文本表`，不含扩展名。中文文件名是当前实际选择，不需要改成旧计划中的 `Texts.csv`。

| 部分 | 当前职责 |
| --- | --- |
| Bootstrap | 创建 TextManager，在启动游戏前传入 ResourceManager 并初始化 |
| ResourceManager | 加载 TextAsset，不负责拆分文本数据 |
| TextManager | 解析文本表，保存字典，按 ID 返回文字 |
| InteractableObject | 保存自己的文本 ID，交互时查询并输出文字 |
| UIManager | 现有 UI 管理；交互文字 UI 尚未接入 |

当前读取与查询约定：

- `LoadTexts()` 跳过首行表头，按换行拆分记录、去掉行尾回车并跳过空白行；表头目前按约定填写，不做名称校验。
- `ParseCsvline()` 保留用户现有拼写，处理引号内英文逗号、连续双引号表示一个文字双引号，以及引号未闭合时返回空数组。当前是支持约定格式的单行解析器，不是完整 CSV 格式校验器。
- 用户明确暂不支持单元格内实际换行，每条记录占一个物理行。以后有需要再讨论；UI 自动换行不属于这里的多行 CSV 支持。
- `LoadTexts()` 检查两列格式、整数编号和表内重复编号；错误行输出日志并跳过，其他正常行继续加入字典。
- 资源加载成功后先 `_texts.Clear()` 再填充，避免重复加载时将旧记录当作新表重复编号；资源加载失败时保留原有字典。当前是清空后逐行导入，未实现整表校验通过后统一替换。
- `GetText()` 使用 `TryGetValue`；编号不存在时输出错误并返回空字符串。`Interact()` 收到 null 或空字符串时直接结束，不再打印空日志。
- 启动时加载，交互时查询已有字典；没有新增每次交互重读文件或自动监听 Excel 的逻辑。
- 逐条打印编号与文字的测试日志已移除，保留加载数量和错误日志。面向玩家的文本集中管理，开发日志继续由代码输出。

## 七、教学方式与沟通要求

- 使用中文，语气友好、清楚，可以称呼用户“宝宝”。
- 一次讲一个小知识点，安排一个可完成的小任务。
- 先解释“是什么、为什么做、完成后解决什么”，再给任务。
- 框架或数据功能先讲清数据从哪里来、交给谁处理、最后到哪里。
- 重点检查逻辑、结构、对象引用、初始化顺序和生命周期。
- 不把一般手打拼写、大小写或排版差异当成教学重点；影响编译、Unity 回调或引用的错误仍需清楚指出。
- 尊重用户自己选择的颜色和细节；`InPutManager` 的类名与文件名拼写明确保留。
- 用户没看懂时先停下来解释，不连续推进新概念。

每轮代码教学按以下方式：

1. 读取实际项目代码，确认当前进度。
2. 解释当前小任务的用途和执行流程。
3. 对尚未掌握的关键字或 API 给出解释和必要片段。
4. 让用户亲自编写代码或操作 Unity。
5. 用户完成后重新读取实际文件，检查实现。
6. 附上本次改动范围的完整参考方法或脚本，供对照。
7. 明确实际验证结果与尚未验证的部分，再决定下一步。

避免重复贴不相关的大段代码。参考代码围绕本轮修改；修改一个方法时，通常给这个方法的完整版本即可。

## 八、代码操作权限与工程模式

- 新功能默认由用户亲自编写。“继续”“下一步”“帮我看看”不等于授权直接代写玩法代码。
- 用户明确要求直接修改时，按本轮授权执行，例如已授权的注释、分区、排版和文档整理。
- 检查、讲解与规划可以直接进行，无需每一步重复确认。
- 不自动创建整套场景、玩家、UI 或玩法实现，替代用户的学习过程。
- 以实际工程文件、场景、预制体和设置为准，历史聊天和截图用于补充背景。
- 现行模式：在编辑器中制作预制体外观、布局和必要引用，代码负责加载、实例化、初始化、行为与显示控制。
- Bootstrap 通过代码创建管理器的现有方式继续保留；不恢复为纯代码搭建所有 UI 的旧模式。
- 游戏内跨系统通知适合使用事件；移动状态和交互按键继续通过输入管理器查询，不要求所有调用都改成事件。

## 九、注释与固定分区要求

完整规范见 [脚本分区与注释规范.md](脚本分区与注释规范.md)，模板见 [MonoBehaviourTemplate.cs.txt](Templates/MonoBehaviourTemplate.cs.txt)。

- 类和方法用简短中文 `<summary>` 说明功能。
- 参数用 `<param>` 说明作用；有返回值时写 `<returns>`；泛型类型参数使用 `<typeparam>`。
- 每个字段、局部变量和 foreach 迭代变量分别说明“保存什么、起什么作用”。
- 复杂方法按“第一步、第二步……”标注关键执行流程；简单单步方法不硬凑步骤。
- 注释简短、关键，随当前代码更新，不写长篇背景和未来计划。
- 使用普通注释分隔，不使用 `#region`。

所有脚本固定保留以下八个分区，未使用的分区也保留：

```csharp
// ==================== 字段 ====================
// ==================== Unity 生命周期 ====================
// ==================== 初始化 ====================
// ==================== 对外接口 ====================
// ==================== 核心逻辑 ====================
// ==================== 事件响应 ====================
// ==================== 内部辅助 ====================
// ==================== 调试显示 ====================
```

保留分区不等于添加空方法。常量类、普通类和编辑器工具保留空标签即可，不因此改变继承关系。

## 十、Git 协作方式

- Git 由用户操作。默认不代为暂存、提交、推送或回滚；如用户以后明确改变授权，再按最新要求执行。
- 用户给出待提交列表或截图时，按显示顺序说明勾选哪些，并提供可复制的提交说明。
- 用户只要提交内容时，给出覆盖当前实际改动的说明，不把玩法修改误写成仅注释整理。
- 结合实际 diff 判断哪些保留、哪些还原，不按文件扩展名一概处理。
- 新增 Unity 脚本、预制体等资源与其 `.meta` 配套提交。
- 保留用户已有的未提交修改。注释和排版任务核对整理前后的代码内容，避免改变逻辑或序列化字段。
