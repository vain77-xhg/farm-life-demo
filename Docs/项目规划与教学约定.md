## 四、当前真实项目基线

截至记录时，工程有 14 个项目 C# 脚本。主要能力如下：

- `Bootstrap` 是现有启动入口，处理单例与 `DontDestroyOnLoad`，运行时创建资源、UI、输入、事件和场景管理器，再传入依赖。
- `ResourceManager` 目前只提供 Resources 预制体加载和实例化方法，尚未实现文本表加载。
- `EventManager` 支持无参数、int 参数和 string 参数事件。
- `InPutManager` 发布界面事件，并提供移动、奔跑和 E 键交互输入查询。
- `SceneLoader` 使用协程等待异步加载，有重复请求拦截、场景可加载检查、进度和完成日志。
- `UIManager` 创建并复用背包与设置预制体；`SettingsUI` 处理关闭按钮。背包目前是界面开关，没有物品存储、数量和格子数据逻辑。
- `FarmSceneController` 创建玩家、传入输入管理器，并设置相机跟随目标。
- `PlayerController` 在 Update 读取方向和交互键，在 FixedUpdate 设置 `Rigidbody2D.velocity`，支持走路和左 Shift 奔跑。
- `CameraFollow` 在 LateUpdate 跟随玩家 X、Y 坐标并保留相机 Z 坐标。
- 交互使用 `Physics2D.OverlapCircleAll` 获取附近碰撞体，通过 `GetComponent<InteractableObject>()` 筛选，再按位置距离选择最近的可交互组件。
- `InteractableObject` 当前保存 `_interactionMessage`，交互结果仍输出到 Console，尚未接入游戏内文字面板。
- 农场已有 `TestObstacle` 与 `FarmSing` 两个测试目标，分别保存不同提示文字；名称以工程实际拼写为准。
- 交互范围使用红色 Gizmos 显示。玩家预制体已保存 `_interactRadius = 0.8`，用户确认手感舒服；脚本中的 `1.5f` 是默认值，不要因此重置预制体配置。
- `GameEvents` 与 `GameScenes` 继续用于事件名称和场景名称。
- 编辑器菜单“工具/打开启动场景”用于打开 `SampleScene`。

启动时要从 `SampleScene` 进入。直接运行没有 Bootstrap 的 `FarmScene`，不能据此认定输入或事件系统断裂。

`Bootstrap.StartGame()` 目前仍保留自动打开背包、创建并隐藏 TestCube 的启动测试。它们属于后续可整理内容，尚未清理。

最近目标选择代码已经实现并做过代码检查。用户明确暂缓了那次多目标运行测试，不要将它写成已通过，也不要把它当成进入文本表教学的前置任务。

尚未实现：文本配置表、`TextManager`、文本 ID 查询、游戏状态管理、时间系统、物品数据系统、背包存储和存档系统。

## 五、ID 与配置数据的规划

当前建议使用可读的字符串 ID，通过前缀、字段名、数据表和查询入口区分类别。

| 类别 | 含义 | 规划示例 |
| --- | --- | --- |
| 文本 ID | 一条显示文字 | `text.sign.farm_notice` |
| 物品 ID | 一种物品的定义 | `item.carrot` |
| 作物 ID | 一种作物的生长配置 | `crop.carrot` |
| NPC ID | 一个 NPC 的配置 | `npc.mayor` |
| 对话 ID | 一段对话流程 | `dialogue.mayor.first_meeting` |
| 任务 ID | 一个任务的配置 | `quest.first_harvest` |
| 配方 ID | 一个制作配方 | `recipe.carrot_soup` |
| 地图 ID | 一张地图的配置 | `map.farm` |

命名与引用约定：

- 小写英文、数字和下划线组成名称，用点分隔类别。
- 同类数据 ID 唯一；被引用的 ID 保持稳定，不随显示名称改变。
- 字段明确写用途，例如 `_textId`、`itemId`、`NameTextId`、`DescriptionTextId`。
- 查询入口分别表达用途，例如 `GetText(textId)` 和 `GetItem(itemId)`。
- 物品表通过 `NameTextId`、`DescriptionTextId` 引用文本表，不把物品身份和显示文字混在一起。
- 定义 ID 表示“哪一种数据”。需要独立存档的具体场景实体，以后再设计实例 ID；当前路牌不用额外引入实例 ID。
- 不同系统按开发进度建立对应表，不要求当前同时实现全部类别。

示例关联：

```text
背包保存 item.carrot 和数量
    → 物品表查到 NameTextId = text.item.carrot.name
    → 文本表查到“胡萝卜”
    → 界面显示名称和数量
```

## 六、计划中的文本数据流

```text
Excel / WPS 编辑 Id、Text
    → 导出 UTF-8 CSV
    → Unity 导入为 TextAsset
    → 启动时读取并解析
    → TextManager 保存 ID 与文字的字典
    → 物体交互时按文本 ID 查询
    → 返回文字
    → 当前输出日志，后续接游戏 UI
```

CSV 计划位置：`Assets/Resources/Data/Texts.csv`。这是计划路径，记录时尚未创建。

计划中的职责：

| 部分 | 职责 |
| --- | --- |
| Bootstrap | 启动时组织文本系统初始化 |
| ResourceManager | 读取文本资源 |
| TextManager | 解析文本表，保存字典，按 ID 返回文字 |
| InteractableObject | 保存自己的文本 ID，交互时请求文字 |
| UIManager | 后续负责显示取得的文字 |

启动时加载一次，交互时查询已准备好的字典。Unity 导入 TextAsset 不会自动建立 ID 查询，解析和查找代码仍需实现。

第一步只做当前两段路牌文字。文本表先用 `Id`、`Text` 两列，具体解析实现和导入工具尚未确定。后续需处理重复 ID、缺失 ID 等实际情况。

面向玩家的文本逐步集中管理；检测数量、加载进度等开发日志继续由代码输出。

## 七、教学方式与沟通要求

- 使用中文，语气友好、清楚，可以称呼用户“宝宝”。
- 一次讲一个小知识点，安排一个可完成的小任务。
- 先解释“是什么、为什么做、完成后解决什么”，再给任务。
- 框架或数据功能先讲清数据从哪里来、交给谁处理、最后到哪里。
- 重点检查逻辑、结构、对象引用、初始化顺序和生命周期。
- 不把一般手打拼写、大小写或排版差异当成教学重点；影响编译、Unity 回调或引用的错误仍需清楚指出。
- 尊重用户自己选择的颜色和细节；`InPutManager` 的类名与文件名拼写明确保留。
- 用户没看懂时先停下来解释，不连续推进新概念。

每轮代码教学按以下方式：

1. 读取实际项目代码，确认当前进度。
2. 解释当前小任务的用途和执行流程。
3. 对尚未掌握的关键字或 API 给出解释和必要片段。
4. 让用户亲自编写代码或操作 Unity。
5. 用户完成后重新读取实际文件，检查实现。
6. 附上本次改动范围的完整参考方法或脚本，供对照。
7. 明确实际验证结果与尚未验证的部分，再决定下一步。

避免重复贴不相关的大段代码。参考代码围绕本轮修改；修改一个方法时，通常给这个方法的完整版本即可。

## 八、代码操作权限与工程模式

- 新功能默认由用户亲自编写。“继续”“下一步”“帮我看看”不等于授权直接代写玩法代码。
- 用户明确要求直接修改时，按本轮授权执行，例如已授权的注释、分区、排版和文档整理。
- 检查、讲解与规划可以直接进行，无需每一步重复确认。
- 不自动创建整套场景、玩家、UI 或玩法实现，替代用户的学习过程。
- 以实际工程文件、场景、预制体和设置为准，历史聊天和截图用于补充背景。
- 现行模式：在编辑器中制作预制体外观、布局和必要引用，代码负责加载、实例化、初始化、行为与显示控制。
- Bootstrap 通过代码创建管理器的现有方式继续保留；不恢复为纯代码搭建所有 UI 的旧模式。
- 游戏内跨系统通知适合使用事件；移动状态和交互按键继续通过输入管理器查询，不要求所有调用都改成事件。

## 九、注释与固定分区要求

完整规范见 [脚本分区与注释规范.md](脚本分区与注释规范.md)，模板见 [MonoBehaviourTemplate.cs.txt](Templates/MonoBehaviourTemplate.cs.txt)。

- 类和方法用简短中文 `<summary>` 说明功能。
- 参数用 `<param>` 说明作用；有返回值时写 `<returns>`；泛型类型参数使用 `<typeparam>`。
- 每个字段、局部变量和 foreach 迭代变量分别说明“保存什么、起什么作用”。
- 复杂方法按“第一步、第二步……”标注关键执行流程；简单单步方法不硬凑步骤。
- 注释简短、关键，随当前代码更新，不写长篇背景和未来计划。
- 使用普通注释分隔，不使用 `#region`。

所有脚本固定保留以下八个分区，未使用的分区也保留：

```csharp
// ==================== 字段 ====================
// ==================== Unity 生命周期 ====================
// ==================== 初始化 ====================
// ==================== 对外接口 ====================
// ==================== 核心逻辑 ====================
// ==================== 事件响应 ====================
// ==================== 内部辅助 ====================
// ==================== 调试显示 ====================
```

保留分区不等于添加空方法。常量类、普通类和编辑器工具保留空标签即可，不因此改变继承关系。

## 十、Git 协作方式

- Git 由用户操作。默认不代为暂存、提交、推送或回滚；如用户以后明确改变授权，再按最新要求执行。
- 用户给出待提交列表或截图时，按显示顺序说明勾选哪些，并提供可复制的提交说明。
- 用户只要提交内容时，给出覆盖当前实际改动的说明，不把玩法修改误写成仅注释整理。
- 结合实际 diff 判断哪些保留、哪些还原，不按文件扩展名一概处理。
- 新增 Unity 脚本、预制体等资源与其 `.meta` 配套提交。
- 保留用户已有的未提交修改。注释和排版任务核对整理前后的代码内容，避免改变逻辑或序列化字段。
