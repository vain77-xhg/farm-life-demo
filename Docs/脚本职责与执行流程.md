## 一、启动入口：先创建，再传引用，最后使用

| 脚本 | 当前任务 | 关键方法、调用者与数据去向 |
| --- | --- | --- |
| [Bootstrap](../Assets/ScriptsCshrp/Bootstrap/Bootstrap.cs) | 保留唯一启动入口，创建和初始化管理器，启动场景流程。 | Unity 调用 `Awake()`；它依次调用 `CreateManagers()`、`InitializeManagers()`、`StartGame()`。`CreateManager<T>()` 创建子对象并添加管理器组件。各个 `Get...Manager()` 把已有组件引用交给调用者，不创建第二份管理器。 |

`Awake()` 先检查 `Bootstrap.Instance`，重复入口会销毁自己；保留的入口调用 `DontDestroyOnLoad(gameObject)`。运行时创建的管理器作为它的子对象，随入口跨场景保留。

创建管理器与初始化管理器是两件事。UIManager 保存资源、事件、状态、时间和文本管理器引用；TimeManager 保存同一份 GameStateManager。文本加载和时间初始化完成后，StartGame 才创建时钟。

StartGame 先 ShowTimeUI，再保留打开背包、创建并隐藏 TestCube、发布 FarmScene 请求。启动背包打开时暂停时钟，关闭后继续。

### 时间的真实值与界面显示分开

TimeManager 由 Bootstrap 创建，Initialize(GameStateManager) 保存共享状态引用。初始为第 1 天 06:00（6*60），每 0.7 现实秒推进 1 游戏分钟，跨日不清零；禁止推进时在累计前返回并保留余量。GetHour=/60%24，GetMinute=%60，GetDay=/(24*60)+1。临时分钟日志保留。

TimeUI 继承 UIBase。UIManager.ShowTimeUI 用 CreateUI<TimeUI>("UI/TimeUI") 创建并缓存，首次传入 TimeManager 和 TextManager，之后直接调用自身 Show；不写入 _currentUI，不触发玩家或时钟权限更新。TimeUI 初始化时查询 400001“第{0}天”并缓存，Update 调用 RefreshTime，分别更新 DayText 和时间文字；内部逐分钟推进，时间显示按十分钟向下取整。

UIManager 的 `_inventoryUI`、`_settingsUI` 缓存具体脚本组件；`_interactionUI` 同样缓存提示组件，`_currentUI` 用 `UIBase` 类型记录当前背包、设置或提示。因此统一入口能调用共同功能，同时各界面仍保留自己的控件逻辑。

`CreateUI<T>()` 的步骤是：资源管理器创建预制体实例 → `GetComponent<T>()` 获取预制体根对象上已有的脚本 → 检查失败并清理无效实例 → 设置父对象、隐藏待用 → 返回组件。它不再另外 `AddComponent<T>()`，以免绕开预制体上保存的引用。

### 每个界面的规则，与当前生效的权限

这两处都有 `CanPlayerControl()`，保存的含义不同：

| 位置 | 保存什么 | 谁读取 |
| --- | --- | --- |
| `UIBase` | “显示这个界面时，是否允许操作玩家”的规则。默认 false，具体实例也受预制体保存值影响。 | UIManager 在显示目标界面时读取。 |
| `GameStateManager` | 玩家“现在”是否允许操作的结果，初始为 true。 | PlayerController 每帧和物理更新时读取。 |

当前数据方向是：界面规则 → `UIManager.ShowUI()` → `GameStateManager.SetPlayerControl(...)` → `PlayerController` 查询并决定是否移动或交互。界面自己不查找玩家并修改速度。

### 统一关闭：功能入口交给公共方法校验

用户已将 `UIManager.CloseSettings()` 修为 `CloseUI(_settingsUI);`。CloseInventory 同样传入自己的背包组件；它们只说明“要关闭谁”，由 CloseUI 统一检查目标非空且确为当前界面，再隐藏、清空记录并恢复玩家操作权限。

设置目标校验与权限恢复调用链已接通；用户已对含设置开关在内的所列 7 项 UI 运行检查反馈无问题。助手未独立编译或运行。CloseSettings 保持 private，EventManager 通过已登记的回调调用它，不需要为阅读位置改成 public。

切换界面时 `ShowUI()` 直接调用 `CloseCurrentUI()` 是有用意的：先隐藏旧界面，再应用新界面的规则，不在切换中途先恢复玩家操作。主动关闭当前界面、回到游玩时，才经 `CloseUI()` 恢复权限。

交互提示现在通过 `ShowUI/CloseUI` 管理：没有缓存时 CreateUI<InteractionUI> 创建，正确检查 `_interactionUI`，SetText 后 ShowUI，再启动新的约 3 现实秒计时。预制体允许操作玩家；界面基类默认 false 并不会覆盖该预制体保存的 true。

切换或关闭当前 UI 时，CloseCurrentUI 停止旧计时并隐藏当前界面。WaitForSecondsRealtime 等待结束先清空协程句柄，再 CloseUI(_interactionUI)；统一入口检查目标仍为当前界面，避免误关新界面。重复提示重启计时，关闭保留实例复用。创建失败保留旧界面已完成代码分支检查，未故障注入运行验证。

玩家移动是给 `Rigidbody2D.velocity` 设置速度，由物理系统推动带刚体的玩家对象；不是相机推动地图。移动方向会归一化，避免斜向比横向更快；走路和按住左 Shift 的跑步使用不同速度。

禁止操作时，`Update()` 清空方向并跳过 E 键处理，`Move()` 把刚体速度清零。输入管理器自身仍处理 Tab/ESC，所以玩家不能移动时仍能操作界面快捷键。

交互检测结果只是附近的 `Collider2D`，并不保证都可交互，也不保证每个都会阻挡玩家。带有 `InteractableObject` 的目标才进入距离比较，最后只调用最近目标一次。Gizmos 红圈只是编辑器中的范围提示。

## 七、阅读代码时记住的四件事

1. `Initialize()` 是普通方法，需要调用者主动执行。方法被放进“初始化”分区，或方法名字叫 Initialize，都不会让 Unity 自动执行它。
2. 订阅事件是在登记回调，不会立即执行回调。只有对应 `Publish` 发生时，事件管理器才会调用已登记的方法；销毁时应取消相应订阅。
3. `SetActive(false)` 是隐藏并停用 GameObject，不是 `Destroy`。管理器仍保留组件引用，所以之后能显示同一个实例；销毁时才需要重新创建。
4. 子类没有自己写方法，也能使用继承的方法。InventoryUI 当前就通过 UIBase 获得显示、隐藏和操作规则查询功能。

八个固定分区只是阅读位置：字段存数据；Unity 生命周期放引擎回调；初始化准备依赖；对外接口集中功能入口；核心逻辑实现功能；事件响应可放通知回调；内部辅助复用操作；调试显示画辅助信息。空分区保留，不必添加空方法。固定分区内还可按功能分组，例如 UIManager 的背包、设置、交互提示小组；已作为事件回调的 CloseSettings 可以和设置方法放在一起，仍保持 private。分区不决定方法何时执行，也不改变访问权限。
