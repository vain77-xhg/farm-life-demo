# 脚本分区与注释规范

这份规范用于当前 Unity / 团结引擎学习项目。目标是打开一个脚本后，能很快找到它保存的数据、何时开始工作、供谁调用，以及具体功能写在哪里。

## 先区分“语法要求”和“项目约定”

`// ==================== 字段 ====================` 是普通注释。分区的名称、数量、排列顺序都是为了方便阅读，不影响程序执行，也不是 C# 必须具备的语法。

真正需要遵守的是：

- 需要挂到 GameObject 上的普通组件继承 `MonoBehaviour`，脚本文件名与组件类名保持一致。
- Unity 生命周期函数的名称、大小写和签名要准确，例如 `Awake()`、`Update()`、`FixedUpdate()`。Unity 才能按对应时机调用它们。
- `Initialize()` 是我们自己定义的方法，必须由其他代码主动调用。把它放在“初始化”分区，不会让它自动执行。
- 字段的声明、方法参数、返回值、引用获取、事件订阅与清理，需要符合实际功能。分区注释不能代替这些代码。

例如，项目中保留 `InPutManager` 这个类名，文件名也保持 `InPutManager.cs`。此次整理不改动已有名称。

我们约定：类和重要方法写中文 XML 文档注释；用普通注释分隔分区；不使用 `#region`；没有内容的分区直接删除。

## 推荐排列顺序

| 分区 | 放什么 | 什么时候需要 |
| --- | --- | --- |
| 字段 | Inspector 配置、运行时引用、运行时状态、常量 | 有需要跨方法保存的数据时 |
| Unity 生命周期 | Awake、Start、Update、FixedUpdate、LateUpdate、OnDestroy 等 | 只写实际需要的回调 |
| 初始化 | Initialize，以及创建或传入依赖的准备方法 | 需要单独准备对象或传入依赖时 |
| 对外接口 | 其他脚本需要调用的功能入口 | 有公开功能入口时 |
| 核心逻辑 | 组件负责的实际功能 | 按功能命名更清楚，例如“玩家移动” |
| 事件响应 | 事件回调、按钮点击回调 | 有对应回调，而且适合单独归类时 |
| 内部辅助 | 被其他方法复用的辅助方法 | 有辅助方法时 |

这不是要求每个脚本都有七个分区。短脚本可以只有“字段”和“初始化”；常量脚本可以只有“场景名称”；编辑器工具可以使用“字段”和“菜单入口”。

同一功能的入口和内部方法可以放在一起。例如 `UIManager` 的打开、关闭和切换背包方法统一放在“背包界面”中，不必为了区分 public/private 而拆散它们。

## 方法在文件里的位置，不等于执行顺序

方法放到上面或下面，主要影响阅读。实际执行取决于 Unity 的调用时机和代码中的调用关系。

当前玩家创建流程是：

```text
FarmSceneController.Start()
  → CreatePlayer()
  → ResourceManager.InstantiatePrefab("Prefabs/Player")
  → 激活的玩家实例触发 PlayerController.Awake()，获取自身刚体
  → PlayerController.Initialize(inputManager)，保存外部输入管理器
  → CameraFollow.Initialize(player.transform)，设置跟随目标
```

所以即使 `Initialize()` 在文件里排在 `Update()` 后面，当前项目仍然是创建玩家时先主动调用初始化，之后才由 Unity 执行玩家的逐帧逻辑。

| 常用回调 | 当前项目中的用途 |
| --- | --- |
| Awake | Bootstrap 创建管理器；PlayerController 获取自身 Rigidbody2D |
| Start | FarmSceneController 开始创建场景中的玩家 |
| Update | 玩家读取方向和 E 键；输入管理器检查界面快捷键 |
| FixedUpdate | 根据输入设置玩家刚体速度 |
| LateUpdate | 相机跟随玩家，保留相机自己的 Z 坐标 |
| OnDestroy | UIManager、SceneLoader 取消事件订阅；SettingsUI 移除按钮监听 |

`OnEnable`、`OnDisable` 等回调以后有需要再加。当前组件通过 `Initialize` 获得依赖时，不要仅为了凑齐模板，把订阅直接搬到可能更早执行的 `OnEnable` 中。

## 字段如何排列

建议按下面三类排列，用短注释说明用途即可：

```csharp
// Inspector 配置：预制体中可调整的移动速度。
[SerializeField] private float _moveSpeed = 3f;

// 运行时引用：初始化时由场景入口传入。
private InPutManager _inputManager;

// 运行时状态：本帧读取的移动方向。
private Vector2 _moveDirection;
```

`[SerializeField]` 的用途是让 Unity 序列化这个私有字段，并在 Inspector 中显示。它不会自动给字段查找对象或赋值。当前玩家的 `_moveDirection` 也标记了这个特性，主要是为了在 Inspector 中观察输入；是否使用该特性要看字段的具体用途。

已有预制体或场景保存了字段数据时，随意改字段名可能影响原有序列化数据。整理注释和顺序时保留现有字段名及其特性。

## 方法注释如何写

注释先说明“做什么”，必要时再说明调用条件、重要步骤和结果。避免把每一行代码重新翻译一遍。

```csharp
/// <summary>
/// 保存输入管理器引用，供玩家读取移动和交互输入。
/// </summary>
/// <param name="inputManager">Bootstrap 已经创建的输入管理器。</param>
public void Initialize(InPutManager inputManager)
{
    _inputManager = inputManager;
}
```

我们按以下规则使用 XML 标签：

- `<summary>`：说明类或方法的职责。
- `<param name="参数名">`：有参数时，说明每个参数代表什么，名称与代码一致。
- `<returns>`：方法有返回值时，说明返回什么；`void` 方法不写。协程的 `IEnumerator` 也属于返回值。
- `<typeparam name="T">`：泛型方法有类型参数时，说明该类型的用途，例如 `CreateManager<T>`。

这些文档标签是我们的注释规范，缺少它们通常不会阻止 C# 代码运行。XML 写正确后，编辑器可以在查看方法时显示说明。

字段通常使用简短的 `//` 注释；公开常量和重要字段可以使用 XML 注释。不要为了注释数量给每个局部变量都写一段说明。

## 事件和初始化如何标注

`Initialize` 的注释应说明依赖从哪里来、保存哪些引用、是否订阅事件。回调方法应说明响应哪个事件。

有订阅就要考虑何时取消订阅。当前项目的 `UIManager` 和 `SceneLoader` 在初始化时订阅，在销毁时取消；`SettingsUI` 在初始化时注册按钮监听，在销毁时移除。注释与这套实际生命周期保持一致。

不要只看见一个 `OnDestroy` 就认为事件管理已经完成，还要能找到与它配对的订阅代码。

## 新脚本怎么使用模板

完整分区骨架见 [MonoBehaviourTemplate.cs.txt](Templates/MonoBehaviourTemplate.cs.txt)。它放在 `Docs` 下，使用 `.cs.txt` 扩展名，供复制参考，不作为游戏组件参与编译。

1. 在 Unity 中创建需要的 C# 脚本，使用实际功能名称，例如 `InteractableObject`。
2. 参考模板，保持类名与新文件名一致，先写清楚类的职责。
3. 只保留当前需要的分区，再逐步填入字段和方法。
4. 新增重要方法时补充 summary；有参数、返回值或泛型类型参数时补充对应标签。
5. 写完检查：引用由谁提供、方法由谁调用、订阅在哪里解除。然后再运行测试。

模板不会自动帮我们创建对象、传入引用或订阅事件。代码功能仍然需要一步一步实现。
